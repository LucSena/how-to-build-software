# Mobile Releases and Operations

## Release pipeline

- **CI builds every merge** into signed artifacts (Xcode Cloud/Fastlane/GitHub Actions/Bitrise/EAS Build — any is fine); signing keys and store API keys in the CI secret store, never in the repo.
- **Versioning:** user-visible semantic version + monotonically increasing build number generated by CI.
- **Tracks:** internal (team, every build) → beta (TestFlight external / Play closed testing) → staged production.
- **Automated checks before store upload:** unit/UI tests, lint, size diff, performance benchmarks, privacy manifest/Data safety consistency, required SDK/target API levels (Xcode 26 SDK required since 2026-04-28; Play target API 36 since 2026-08-31).
- **Symbol uploads** (dSYMs, R8 `mapping.txt`, Hermes/JS source maps) are part of the pipeline; unsymbolicated crashes are unreadable.
- **Release notes** written for users ("Fixed: photos failed to upload on slow networks"), not "bug fixes and improvements".

## Rollouts

| Store | Mechanism | Default policy |
|---|---|---|
| Google Play | Staged rollout to a percentage of users; increase or **halt** anytime; Play also supports managed publishing (you choose when an approved release goes live) | 1% → 5% → 20% → 50% → 100% over several days, gated on crash/ANR rate and key business metrics |
| App Store | **Phased release** for automatic updates over 7 days (pausable); users can still update manually; or release to all at once | Use phased release for every update unless it's an urgent fix |

Gates between steps: crash-free users vs previous release, ANR/hang rate, startup time, API error rate, a key funnel metric. Halt first, investigate second. You cannot roll back a binary in either store — you ship a new build (or flip a flag).

## Feature flags and remote config

- Every risky feature ships behind a **server-controlled flag** with a kill switch; default off in code for new features, and the app must behave correctly if config fetch fails (cached/last-known values, safe defaults).
- Target flags by app version, platform, OS version, and cohort; ramp by percentage.
- Remove flags within a release or two after full rollout; stale flags are tech debt and test-matrix explosions.
- Remote config is not a place for secrets or for code — only parameters.
- Remote config may change behavior only within what was reviewed; hiding substantially new features behind a flag to dodge store review violates both stores' rules.

## Forced and prompted updates

- Add a **minimum supported version** check at launch (from remote config or an API header) *before* you need it — old versions live for years.
- Levels: *soft* (dismissible banner "Update available"), *hard* (blocking screen with one action: Update) only for security issues, legally required changes, or broken backward compatibility.
- Android: Play **In-App Updates** API — flexible (background download, then restart prompt) or immediate (full-screen blocking flow).
- iOS: no system API; show your screen with a link to the App Store page; don't block while the new version is still in phased release for others (check availability).
- Keep the backend compatible with all versions above the minimum; version your API and tolerate unknown fields.

## OTA updates (React Native / Expo)

Rules (store policy):
- **Apple:** interpreted code may be downloaded only if it does not change the app's primary purpose by adding features inconsistent with what was reviewed, does not create a storefront for other code, and does not bypass signing, sandbox, or OS security (Developer Program License Agreement 3.3.1(B)). App Review 2.5.2 forbids downloading code that introduces or changes features.
- **Google Play:** apps may not download executable native code (dex, JAR, `.so`) from outside Play; code running in a VM/interpreter (e.g. JavaScript) is allowed but must not enable policy violations.

Practice:
- Use OTA for bug fixes, copy/asset changes, and small tweaks to reviewed features; ship new features and anything touching native code through the stores.
- Bind every update to a **runtime version** (Expo `runtimeVersion`, e.g. the fingerprint policy) so JS never runs against an incompatible native binary.
- Roll out OTA updates gradually (percentage/channels), monitor crashes per update ID, and keep one-command rollback.
- Decide the update-check strategy: check on launch, apply on next launch by default; apply immediately only for critical fixes with a clear reload moment.
- Sign updates (code signing in EAS Update) so a compromised CDN can't push code.

## Deep links

| Platform | Setup | Verify |
|---|---|---|
| iOS Universal Links | Host `apple-app-site-association` (JSON, no redirect, HTTPS) at `https://<domain>/.well-known/`; Associated Domains entitlement `applinks:<domain>`; handle in `onOpenURL` / `NSUserActivity` | Install from TestFlight and tap links in Notes/Messages; AASA is fetched via Apple's CDN, so changes take time |
| Android App Links | Host `assetlinks.json` at `https://<domain>/.well-known/` with the release signing-certificate SHA-256 (and Play App Signing key); intent filter with `android:autoVerify="true"` | `adb shell pm get-app-links <package>`; Play Console deep-link tools |
| Custom schemes | `myapp://` — fallback only (any app can claim a scheme) | — |

Design rules:
- Map every URL to a route in the navigation model (Navigation 3 back stack, `NavigationStack` path, Expo Router file routes) and **synthesize a sensible back stack** (Home → List → Item).
- Handle: not logged in (log in, then continue to the target), item not found/deleted, no permission, unsupported old link formats, app not installed (web fallback page).
- Treat link parameters as untrusted input: validate IDs, never auto-execute destructive actions from a link.
- Deferred deep links (install → open to content) need an attribution/linking service; Firebase Dynamic Links has been shut down, so choose a maintained provider or a first-party solution.

## Push notification infrastructure

- **Registration:** request permission in context (see `mobile-design`), obtain the APNs device token / FCM registration token, send it to your backend with user ID, platform, app version, locale, and notification preferences. Refresh on token change and app update; delete on logout.
- **Backend:** a notification service with templates, per-category user preferences, quiet hours, frequency caps, deduplication (collapse keys / `apns-collapse-id`), and delivery logging. Remove tokens the provider reports as invalid.
- **Payload:** minimal — IDs and display text; no sensitive personal data (lock screens are public); localized server-side or with localization keys.
- **Types:** visible alerts; data/silent pushes to trigger sync (best-effort, throttled on both platforms); rich notifications via a Notification Service Extension (iOS) or custom styles (Android); Live Activities / Live Updates for ongoing user-initiated tasks.
- **Android specifics:** notification channels by category created at startup; `POST_NOTIFICATIONS` permission (13+); high-priority FCM only for time-sensitive user-visible messages.
- **iOS specifics:** interruption levels (passive/active/time-sensitive/critical); provisional authorization for quiet trials; notification categories with actions.
- **Tap handling:** every notification carries a deep link routed through the same deep-link handler, with back stack synthesis.
- **Marketing** pushes only with explicit opt-in and an in-app opt-out (App Review 4.5.4); never make push a requirement.

## Observability

| Signal | Tooling (examples) | Notes |
|---|---|---|
| Crashes | Crashlytics, Sentry, Bugsnag, Xcode Organizer, Play Console | Symbolicate (dSYM, R8 mapping, JS source maps); alert on new crash clusters per release |
| ANRs / hangs | Play vitals ANR rate; MetricKit hang diagnostics; SDK hang detection | Keep below 0.47% user-perceived ANR rate |
| Exit reasons | Android `ApplicationExitInfo` (incl. Android 17 memory-limit kills); MetricKit crash/exit diagnostics | Log on next launch |
| Performance | Firebase Performance/Sentry tracing, MetricKit, JankStats | Startup, screen render, network latency by version and device class |
| Product analytics | Any privacy-respecting pipeline | No PII; respect ATT and consent; Data safety / App Privacy labels must match |
| Logs | Structured, leveled, sampled; ring buffer attached to crash reports | Never log tokens, passwords, or personal data |

Dashboards per release: crash-free users, ANR/hang rate, startup p50/p90, top errors, adoption curve (to know when a minimum-version bump is safe).

## Incident playbook

1. **Detect:** alert on crash-rate or error-rate regression by release/update ID.
2. **Contain:** halt the staged rollout / pause phased release; flip the feature flag; roll back the OTA update.
3. **Fix:** hotfix branch from the release tag; expedited review request on iOS only when justified.
4. **Recover:** if a bad version is widely installed, raise the minimum supported version (soft first, hard only if necessary).
5. **Learn:** blameless postmortem; add a test, a gate, or a flag so the class of issue can't recur (see `reliability`).
